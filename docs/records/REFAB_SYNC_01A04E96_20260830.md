## 2. 已移植的部分

### 2.1 `ScopePipMinMagnification`（`5a96423` + `c74b34b`）

**她为什么加**：低倍镜（2×/3×）下整屏变焦的观感本来就自然，PIP 却照付每帧全屏拷贝
（二次渲染模式下是整遍世界重画）。于是加一道倍率下限：当前档位倍率低于该值时
PIP 让位、回经典整屏变焦。

**落到这里**：我们已移植的 PIP 与她同构，四个时机（无光影路径 / FOV 让位 / 抓取 /
合成）同样全部经由 `isEnabledForHeldGun()` → `inactiveReason()` 覆盖，
`wantsIrisComposite()` 是光影路径的另一半，所以这两处加闸门即可覆盖全部路径
（已逐行核对调用点：本仓 5 处，她 5 处，结构一致）。

| 文件 | 改动 |
|---|---|
| `config/client/RenderConfig.java` | 新增 `SCOPE_PIP_MIN_MAGNIFICATION` 字段与 `defineInRange("ScopePipMinMagnification", 4.0d, 1.0d, 100.0d)`（ForgeConfigSpec → `ModConfigSpec`，其余逐字） |
| `client/render/scope/ScopePipRenderer.java` | `inactiveReason()` 与 `wantsIrisComposite()` 各加一道闸门 + `minMagnification()`（配置未加载时兜底 4.0） |
| `compat/cloth/client/RenderClothConfig.java` | 紧跟 PIP 总开关之后的 double 输入框（1.0~100.0，默认 4.0），写法与本仓已有的 `scope_pip_resolution_scale` 一致 |
| `lang/en_us.json` / `lang/zh_cn.json` | 各 2 条键与文案（逐字） |

默认值 4.0 与她一致（`pip_default = mirror` 裁决）。`1.0` = 旧行为（所有倍镜都 PIP）。
组合镜按**当前档位**判定 —— `scopeMagnification()` 取的就是 `zoom[zoomNumber]`，
切到低倍档自动回整屏变焦、切回高倍档自动回 PIP。

### 2.2 CI 编译检查（`.github/workflows/compile-check.yml`）

**为什么取**：这是本仓当前最大的短板 —— 沙箱里拿不到 JDK、也连不上 Maven 源，
前面三轮都是把未编译的代码交给用户构建才发现问题的（其中两轮就耗在一个
本不该自加的硬件剪裁上）。她的方案是：编译在 GitHub Actions 上跑，日志经
Contents API 写回分支的 `build-reports/compile-java.log`，沙箱用
`gh api contents` 直接读 —— 绕开 Actions 日志 blob 域不可达。

**适配**：只在本仓 `arena/**` 分支触发（与她一致），`paths-ignore: build-reports/**`
防死循环；Java 25（本仓目标版本）；命令 `./gradlew compileJava`。
另加一条 `.gitignore` 把 `build-reports/` 排除在提交之外（API 写入不受影响）。

**暂存在 `docs/ci/compile-check.yml`，没有放进 `.github/workflows/`**：
本沙箱的 GitHub 凭据**没有 `workflows` 权限**，直接推会被拒
（`refusing to allow a GitHub App to create or update workflow ... without
\`workflows\` permission`）—— 她那边的 `fb2ea4c` 正是因此把 v3 暂存到 `docs/ci/`。
需要**项目成员**把它移到 `.github/workflows/compile-check.yml`（内容无需改动），
推上去后本分支就会开始产出编译日志。

## 3. 暂不移植：内置 Mesh Loader（`8c6ad27`）

### 它是什么

移植第三方模组 `VellEagle/TacZMeshLoader`（`1.21.1_fabric` v0.1.7，GPL-3.0）的
`poly_mesh` 解析与渲染，支持枪 / 配件 / 弹药 / 方块四条通道；第 0 步只做
collector 路径，**不含 GPU 烘焙**。

### 判断

| 维度 | 情况 |
|---|---|
| 许可证 | GPL-3.0，本仓同为 GPL-3.0 ⇒ **不构成障碍**（真要移植需在 `LICENSES.md` 具名致谢上游） |
| 上游稳定性 | 她自己的文档列了 **4 次被关闭的 PR**（#33/#69/#70/#71-72），本轮是第五次，且明确是「第 0 步」 |
| 性能收益 | 她**如实声明**：无 GPU 路径 ⇒ 对 36 万顶点级高模的第一人称帧率**没有量级改善**，只有闸门与缓存级削减 |
| 适用前提 | 只有枪包用 `model_type=mesh`（poly mesh）时才有用；立方体枪包完全不受益 |
| 体量与风险 | ~2000 行、4 个新 mixin（打在 `ClientAttachmentIndex`/`ClientAmmoIndex`/`ClientBlockIndex`/`GunDisplayInstance` 上）、新 mixin 配置、Fabric 入口点需改写 |
| 与 AGENTS.md 的冲突点 | 每个注入点都必须**逐条对照本仓源码**核实（本仓是 NeoForge 移植，模型类与她那边的字段/懒加载路径未必一致）；在不能编译的前提下做这件事，正是用户刚批评过的「没做好功课就动手」 |

### 结论

**暂不移植**，等一个决定性事实：*我们是否会用带 mesh 模型的枪包？*
- 会 ⇒ 值得单独开一轮，先做「注入点逐条取证」的功课，再动代码；
- 不会 ⇒ 2000 行代码 + 4 个注入点换不到任何观感收益，不合算。

（`4fb137d` 那笔「镜内二次渲染跳过 poly 顶点写入」只改 `PolyMeshSnapshot`，
我们没有这个类，自然随 mesh 一并推迟。）
