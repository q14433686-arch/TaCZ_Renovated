## 为什么可以「同形移植」

同步前逐文件比对过本线（26.2）与 1.21.11 线 `c3dd078^` 的对应源码：

| 文件 | 差异 |
|---|---|
| `AbstractGunSmithTableBlock.java`、`GunSmithTableBlockB.java`、`StatueBlock.java`、`StatueBlockEntity.java`、`TargetBlockEntity.java`、`TargetOwnerProfiles` 的宿主代码 | **无差异**（逐字节相同） |
| `TargetBlock.java` | 1 行：本线 `player.sendOverlayMessage(...)`（1.21.11 线是 `displayClientMessage(..., true)`） |
| `TargetMinecart.java` | 1 行：本线 `player.sendSystemMessage(...)`（1.21.11 线是 `displayClientMessage(..., false)`） |
| `TargetRenderer.java` | 1 行：本线 `net.minecraft.client.renderer.state.level.CameraRenderState`（1.21.11 线在 `...state.` 下） |
| `TargetMinecartRenderer.java` | 2 行：本线 `submitMinecartContents(..., BlockModelRenderState, ...)`（1.21.11 线是 `BlockState`） |

即：两条线的**生命周期与持久化逻辑完全一致**，只有 26.x 改名后的客户端/聊天 API 不同。因此
方块掉落、雕像持枪、标靶主人这三块按 1.21.11 的修法搬运，保留本线原有的 API 写法，
**不**整文件覆盖。

## 工作台：不能只删手工掉落

旧版 `AbstractGunSmithTableBlock#playerWillDestroy` 在生存模式挖非根半边时手工 `popResource`
一份克隆，而本线另有 `affectNeighborsAfterRemoval`，会在邻接更新之前用
`removeBlock(companion, false)` 静默清除另一半 —— 后者绕过了根半边的战利品表。两处叠加的
结果是「挖非根掉两份或一份都不掉」，与姊妹线直接删手工掉落的场景**不同**，所以本轮
**同时移除**手工掉落与提前清除，把另一半交给 `updateShape` → `Block#updateOrDestroy`。

推演依据（与 1.21.11 线同一套证据，链接见该线记录 `docs/records/SISTER_SYNC_12111_20261027.md`）：

1. `LevelChunk#setBlockState` 里 `affectNeighborsAfterRemoval` 先于邻接形状更新；
2. `Level#setBlock` 向邻居传播标志位时用 `flags & -34`，会清掉 `UPDATE_SUPPRESS_DROPS`，
   `Block#updateOrDestroy` 会对变成空气的邻居调用 `destroyBlock(drop=true)`；
3. 战利品表 `workbench_b.json` / `gun_smith_table.json` 的 `block_state_property` 是
   `part=foot`（C 型是 `half=lower`），并从根方块实体拷 `BlockId` ⇒ 挖哪一半都只产出一份；
4. B 型创造模式的抑制判据由 `bedPart == FOOT` 改为 `== HEAD`（原判据照抄原版 `BedBlock`，
   而原版床的 loot 在 head；我们的 loot 在 foot，没有跟着翻转 ⇒ 创造模式挖任意一半都漏一个）；
5. Carry On 拾取仍由 `CarryOnPickupHandlerMixin` 重定向到根半边，根被移除时邻接更新清掉
   非根半边（非根 loot 不产出），放置时 `onPlace` 重建另一半。

外部模组若用不传播邻接更新的特殊标志或拦截这些事件，不在本轮验证范围。

## 雕像

`StatueBlockEntity#preRemoveSideEffects(BlockPos, BlockState)`：服务端用**传入的移除前状态**取
`FACING`（缓存状态此时可能已是空气，直接 `getBlockState().getValue(FACING)` 会抛
`IllegalArgumentException`；无该属性时回退 `NORTH`），`popResource` 后清空栈避免重复，
并调用 `super`。父类 `StatueBlock` 的注释一并更正 —— 上游 `Block#onRemove` 在 1.21 起已被删除，
26.2 也**没有**「方块实体移除时自动清理」的默认行为，此前只留了一行注释，枪会静默消失。

## 标靶 / 标靶矿车主人

| 项 | 处理 |
|---|---|
| 放置 | `TargetBlock#setPlacedBy` 不再 `new GameProfile(null, 名字)`（authlib 9 的 record 构造器对 id/name 做 `Objects.requireNonNull`，必抛 NPE；抛在 `BlockItem#place` 中途 ⇒ 方块放下但物品不消耗），改用 `TargetOwnerProfiles#fromName` → `ResolvableProfile#createUnresolved` |
| 存档 | `TargetBlockEntity` 对称读写 `owner_name`（可存非玩家名/长名），并调用父类 `loadAdditional/saveAdditional` 以保留 NeoForge 附加数据；缺失字段时清空旧值，损坏的旧 JSON 名称不再让区块读取抛异常 |
| 矿车 | `TargetMinecart#getOwnerProfile` 返回 `ResolvableProfile`，按自定义名变化刷新缓存；改名不再在渲染线程构造 `GameProfile` |
| 客户端皮肤 | 标靶与矿车共用 `TargetOwnerSkins`，走原版异步 `PlayerSkinRenderCache`；解析中/失败回落默认皮肤并只 WARN 一次 |

## 与 1.21.11 线的唯一代码差异：皮肤缓存来源

1.21.11 线的 `TargetOwnerSkins` 用 `Minecraft#playerSkinRenderCache()` 静态取缓存。26.2 侧本线
没有该访问器的可编译证据，改用渲染器构造参数已经携带的缓存：

- 方块实体渲染器：`BlockEntityRendererProvider.Context#playerSkinRenderCache()`；
- 实体渲染器：`EntityRendererProvider.Context#getPlayerSkinRenderCache()`；
- 渲染状态里存 `RenderType`（`PlayerSkinRenderCache#getOrDefault(profile).renderType()`，
  失败回退 `PlayerSkinRenderCache.DEFAULT_PLAYER_SKIN_RENDER_TYPE`），不再自行用
  `RenderTypes.entityCutout/entityTranslucent(Identifier)` 拼皮肤层。

依据：姊妹仓 **26.2 线** `26783689`（PR #117）在 MC 26.2 上用同一组类型与调用，且其
CI 编译记录为 success（`docs/lineage/…` 对应 `ci-log: compile result (success) for 26783689…`）；
`PlayerSkinRenderCache` 属于 `net.minecraft.client.renderer`（vanilla），Fabric/NeoForge 共用。
这仍是**旁证**，不是本仓 NeoForge 编译结果。

同时**不再**使用 `DefaultPlayerSkin.get(profile.partialProfile())` 作为兜底（1.21.11 线那样写），
避免在 26.2 依赖未被本线验证的 `partialProfile()` 路径。

## 编译门风险点（26.2 特有）

| 调用 | 26.2 依据 | 等级 |
|---|---|---|
| `net.minecraft.client.renderer.PlayerSkinRenderCache`、`getOrDefault(profile).renderType()`、`DEFAULT_PLAYER_SKIN_RENDER_TYPE` | 姊妹仓 26.2 线 `26783689`（PR #117）在 MC 26.2 上同形使用，CI success | 旁证（Fabric 26.2 CI） |
| `BlockEntityRendererProvider.Context#playerSkinRenderCache()` | 同上（`block/TargetRenderer.java`） | 旁证 |
| `EntityRendererProvider.Context#getPlayerSkinRenderCache()` | 同上（`entity/TargetMinecartRenderer.java`） | 旁证 |
| `ResolvableProfile#createUnresolved(String)` | 同上；另有 `createUnresolved(UUID)` 重载 | 旁证 |
| `ResolvableProfile#CODEC`（本轮未用，仅记录） | 同上 | 旁证 |
| `ResolvableProfile#name()`（`saveAdditional` 里取名字写 `owner_name`） | 只有 1.21.11 线的 CI 结果；26.2 未直接取证 | **待 CI 验证**：若 26.2 改了访问器，改用 `ResolvableProfile.CODEC` 或 `partialProfile().getName()` |
| `BlockEntity#preRemoveSideEffects(BlockPos, BlockState)`、`BlockState#hasProperty`、`Block#popResource` | 1.21.11 反编译源码 + 本仓既有调用；NeoForge 未覆盖这些签名 | 沿用本仓既有形态 |

vanilla 类在 Fabric/NeoForge 之间共用，因此姊妹 26.2 CI 对 `net.minecraft.*` 的编译结果对本线
有参考价值，但**不能替代**本仓 NeoForge 编译门（构建链、AT、mixin 配置都不同）。

## 本轮验证与边界

- `python3 scripts/verify_block_drops.py --strict`：通过（A–E 五项静态接线）。
- `python3 scripts/verify_block_entity_persistence.py --strict`：通过（含 26.2 皮肤接线规则 G）。
- `python3 tests/test_sister_block_sync.py`：5 组通过（按 loot JSON 与调用顺序建模生存/创造、
  错误判据、掉落规则关闭、Carry On 拾取两半）。
- `python3 tests/test_sync_guards.py`：9 组通过（在临时副本注入相反判据、提前清除、半格类型
  回归、错误的 `BlockId` 拷贝、缺失移除钩子、null 档案/父类调用、放置同步、皮肤回归）。
- `bash scripts/check_release_consistency.sh --strict`：通过。
- 两个守卫脚本为**静态检查**；python 测试为**模型推演**，都不是 Minecraft 引擎运行。
- 本沙箱**没有 JDK / Gradle**（`java`、`javac` 均不存在，外网只放行 GitHub/PyPI/npm），
  因此本仓 26.2 的 `./gradlew build`、`javac` 与实机均**未执行**：`targetProfileTest` /
  `targetBlockEntitiesTest` 已接入 Gradle `check`，需由 CI 回写结果。1.21.11 线的 CI 通过
  不能替代本线 NeoForge 编译门。
